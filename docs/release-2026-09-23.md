# Second pass: photo panning, hydration, dead code

Found by running the app and a two-browser duel rather than by reading, so every
number below is measured.

## Fixed

- **Most of a zoomed photo could not be reached.** `SceneExplorer` capped pitch
  at ±0.7 while yaw had no such cap, so vertical panning stopped at
  `0.7 × 0.48 = 33.6%` of the frame height however far the plate actually
  overhung it. Measured in Chromium: after eight hard upward drags at 2.8×
  zoom the photo travelled **269px of an available 944px — 28%**. The top and
  bottom of every zoomed or portrait plate were unreachable, and 15 of the 142
  bundled plates are portrait (up to 1600 × 3191). The bound now comes only
  from the plate's real overhang, which `apply` already computed and
  renormalised. Re-measured after the fix: **720px of 720px — 100%**.

  The bounds moved into `src/lib/game/scene-transform.ts` so they can be
  tested; six cases cover the tall plate, both axes, a plate that does not
  overhang, runaway drags, zoom, and an unmeasured image.

- **React discarded and rebuilt the entire match UI on every load.** The
  fullscreen button rendered under `typeof document !== "undefined" &&
  document.fullscreenEnabled`, so the server emitted nothing where the client
  emitted a button. React reported a hydration mismatch and regenerated the
  tree. The capability is now read after mount, when both sides agree. The
  error is gone from the console.

- **The match tree re-rendered twice a second during online play.** `emitPeers`
  keyed its change-detection on `rttMs`, which is remeasured on every 2s ping.
  Neither `rttMs` nor `candidateType` is read by any component — they are
  diagnostics only — so every ping re-rendered all consumers for nothing. Both
  stay on the peer object; neither is in the key any more.

- **Removed `src/components/game/scene-viewer.tsx`** (259 lines), which nothing
  imported. `SceneExplorer` and `PanoViewer` are the live viewers.

## Verified working, left alone

A two-context duel was played end to end: both players seated, host started the
match, both pinned and locked, both revealed the same truth with correctly
different scores. Timers stayed in lockstep (24s/24s, 4s/4s) through to a
no-guess expiry on both clients. A host page refresh does **not** break the
room — browser history state preserves the creator flag, so the earlier concern
about that was unfounded.

The next-plate preloader was also checked and is correct: for all 149 enabled
locations it warms exactly the URL the viewer goes on to request.

## Worth a decision, not changed here

**Speed outscores accuracy.** `roundScore = accuracyPoints + timePoints`, each
capped at 10,000. Answering instantly pays ~8,700 whatever the guess, so in the
duel above a **6,924 km miss scored 8,687 of 20,000** with an accuracy
component of 0. Clicking the map centre immediately every round beats studying
the photo. That is the documented design — the README says "Accuracy and speed
both score" — so rebalancing it would change every score, the stored stats and
the stated rules. If it should change, the smallest fix is to scale the time
bonus by accuracy rather than adding it, so speed rewards fast *correct*
answers.

**The three bundled 360 plates are 2560 × 1280.** Over a full sphere that is
~7.1px per degree, which is soft when zoomed. Fixing it needs higher-resolution
source files, not code.

## Verification

`npm run test:game` 123 passed (117 before), `typecheck`, `typecheck:worker`,
`lint` and `build` all pass. The pan and hydration fixes were re-measured in
Chromium after the change; the duel was replayed after the `emitPeers` change
and still syncs.

The Cloudflare match worker remains typechecked but undeployed, so
server-authoritative play is still covered by unit tests and reading only.
